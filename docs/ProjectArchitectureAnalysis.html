OctPlayer 架构分析与实施建议

基于现有代码结构、FFmpeg + Qt Quick + SDL 的分层设计，以及 TodoSteps.html 的执行路线，整理出项目当前状态、关键架构边界和后续优先级。

OVERVIEW

1. 项目定位：这是“播放器内核骨架”，而非成品播放器

从 README 和代码结构看，OctPlayer 是一个带有明确分层边界的播放器骨架，目标是把控制层、解封装、解码、音频输出、视频输出和 Qt 适配层拆开。

结论很明确：当前并不是“能直接播放所有媒体”的成熟播放器，而是已经具备播放器核心抽象与跑通框架能力的工程骨架，重点在“边界清晰、可扩展、可测试”。
已建骨架 已定义状态机 已抽离 API 层 待完成 FFmpeg 解码链路 待完成视频渲染真正输出

从 README 的状态描述可以确认，当前项目已经具备这些要点：

  • 状态转换、生命周期、命令串行化、时钟与同步边界已经建立。
  • FFmpeg demux / decode / stream 发现、大量解码器细节、Seek 与 flush 语义、视频纹理上传等都被设计成“明确扩展点”。
  • 音频、视频和 Qt 适配层是独立的接口，后续可以逐步填充而不动整个架构。
ARCHITECTURE

2. 分层架构：清晰的责任边界

项目最重要的价值在于“分层非常合理”，这让它足以承接后续复杂功能扩展。

API 层

player/api 中承载稳定接口：IPlayer、MediaTypes、PlayerEvent。这里定义媒体源、状态、时间、事件结构，目的是让上层 UI 和底层实现解耦。

核心控制层

player/core 中的 Player、PlaybackSession、MediaClock、AudioClock 是播放器的总控中心。Player 负责串行接收命令；PlaybackSession 负责单次打开/播放/暂停/seek 的会话生命周期。

FFmpeg 后端

backend/ffmpeg 下的 FfmpegDemuxer、PacketQueue、AudioDecoder 等类负责底层封装、pkt 读出和音频解码，仍然暴露出明显的扩展接口。

输出适配层

output/audio 与 output/video 分别绑定 SDL 音频输出和视频帧邮箱（mailbox）。这是实现 A/V 分离和后续渲染时序控制的关键。

Qt 平台层

platform/qt 下的 QtPlayerAdapter、VideoOutputItem、VideoOutputRenderer 负责把播放状态桥接到 QML 和 Quick 场景图。

应用层

app 下的 Main.qml 是最小可交互的演示层，用于打开媒体、播放、暂停、快进、显示时间和绑定视频输出项。

CONTROL FLOW

3. 控制流与状态机：最核心的工程价值

项目真正重要的部分，不是某个播放器 demo，而是“播放器生命周期和状态管理机制”。

从 Player.cpp 可以看到，Player 内部使用命令队列 + 控制线程来串行处理 open/play/resume/pause/stop/seek 等操作，避免 UI 直接跨线程访问播放状态和解码器。这意味着：

  • UI 线程职责单一，负责 QML/Qt 事件；内核通过 controlThread_ 执行状态变化。
  • 每次 open 都会创建新的 PlaybackSession，并立刻将旧 session 置为 stop/失效，确保 session generation 机制有效。
  • 通过 activeSessionId_ 和 activeGeneration_ 过滤旧事件，避免切换媒体时“上一会话的状态事件污染新界面”。
  • PlayerEvent 体系是桥接内部状态与 UI 的关键，事件携带 sessionId、generation 和 payload，显著降低脏状态/竞态风险。
这是一个非常合理的播放器设计：控制流在 Player，真实播放行为在 PlaybackSession，输出适配在 SDL/VideoFrameMailbox，UI 在 QML。它已经非常接近成熟播放器的最小骨架模型。

PlaybackSession 也明确体现了“会话”设计思想：

  • open() -> demuxer_.open()，提取元信息并设置 duration / seekable / tracks。
  • play() -> 启动 demux 线程和音频线程。
  • seek() -> 先 stopDemuxThread / stopAudioThread，再 flush audio/video 缓冲区，然后重新 seek。
  • stop() -> 清理 audio、video、decoder、clock，并进入 Idle 状态。

4. 现状判断：已经完成“架构嫁接”，还没完成“播放能力闭环”

模块 现状 判断
状态机 / 生命周期 已具备骨架和状态转换 较成熟，适合继续扩展
Player 命令队列 已串行化处理 正确且适合后续线程拆分
FFmpeg demux 抽象存在，但读流与 seek 细节还没闭环 下一阶段必做
音频输出 SDL sink 与 resampler 已建立 是最适合优先打通的路径
视频输出 FrameMailbox 和 QtRenderer 已建立，但真正上传纹理/Shader 未完成 待补足真实渲染管线
Seek / flush / EOF / stale session 设计意图已体现 仍需真实测试验证

从代码语义看，最关键的现实判断是：

  • 主架构方向是对的；
  • 当前实现已经建立了“播放器运行时的骨骼”；
  • 真正缺失的是“数据路径的完整闭环”：FFmpeg 读取、解码、音频回调、视频帧消费、seek/flush 与渲染上传。
ROADMAP

5. 下一步路线：按 TodoSteps.html 的顺序最合理

参考 TodoSteps.html 的建议，最优顺序不是“先做视频渲染”，而是“先把可播放骨架闭环，再补视频输出”。

第一阶段：先把播放器骨架跑起来

  • 完善状态机，保证 Idle / Opening / Ready / Playing / Paused / Stopping / Error 的合法转换。
  • 继续串行化命令队列，保证 UI 与控制线程之间没有直接跨线程状态访问。
  • 为会话加上 sessionId + generation，保证切换媒体时忽略旧事件、旧帧和旧错误。

第二阶段：完成 FFmpeg 基础能力

  • 实现 FfmpegDemuxer::read/seek 和 stream discovery。
  • 明确 MediaInfo：时长、音视频流索引、宽高、采样率、声道、seekable。
  • 建立 PacketQueue，并按音频/视频 stream 分发，支持 flush、abort、close 和 reset。

第三阶段：优先打通音频

  • AudioDecoder 作为第一大优先级，实现 PCM 产出。
  • 将 decoded PCM 送入 SDL ring buffer / audio sink。
  • 用 AudioClock 建立时钟，确保音频播放状态和 seek/restart 正确。

第四阶段：视频解码与调度

  • 实现视频解码线程和帧队列。
  • 把解码出来的视频帧交给 VideoFrameMailbox。
  • 在显示前做 pts、时钟同步和帧龄检测。

第五阶段：Qt Quick 视频显示

  • 用 QQuickFramebufferObject 或 OpenGL 纹理上传替换当前的测试图样。
  • 支持 YUV420P / NV12 等经典格式的 shader 转换。
  • 把实际帧直接送入 UI 线程的可显示对象。

第六阶段：make local file playback usable

  • 完善 seek、EOF、重复 seek、stop 和 stale session 处理。
  • 加入生成检查，确保数据帧在 seek 后可被丢弃和重建。
  • 确认本地媒体可以稳定打开和播放。
RECOMMENDATION

6. 最优建议：按“音频优先、视频随后、稳定性最后”的顺序推进

如果要在当前工程上做下一步，最实用的顺序是：

  1. 先做 FFmpeg demux + seek + PacketQueue：这是底层数据入口，没它后面的播放无从谈起。
  2. 再做音频 decoder + SDL sink + AudioClock：音频是通常最容易验证“播放器真的播放了声音”的地方，而且对时钟和状态恢复非常关键。
  3. 再做视频解码和 VideoFrameMailbox：在有稳定音频和时钟基础后，视频渲染会简单很多。
  4. 最后补充 Qt 纹理上传与 shader：在架构稳定后再做显示细节，避免重复推翻结构。
这个顺序和 TodoSteps.html 的路线几乎一致：它强调“不急着看到画面”，而是优先保证 Session 生命周期、时钟、命令串行和输出边界正确。这个方向对工程质量最稳妥。

从工程视角看，OctPlayer 当前最值得做的不是“堆更多功能”，而是把下面这些能力真正打通：

  • FFmpeg demux 正确读包；
  • PacketQueue 可靠工作；
  • AudioDecoder 产出 PCM；
  • SDL sink 真正播放；
  • VideoFrameMailbox 能接收真实视频帧；
  • QtRenderer 能消费并显示；
  • seek/flush/EOF/stale session 能稳定处理。
结论：OctPlayer 当前处于“架构骨架已成立，能力闭环待补齐”的阶段；按照 TodoSteps.html 的规划，最优推进路径是“FFmpeg -> 音频 -> 视频 -> 稳定性与扩展能力”。
